## 1. 프로젝트 배경

창업 입지를 정하려면 유동인구는 공공데이터, 매출은 상권정보시스템, 시세는 부동산 앱, 정책자금은 기관별 공고에서 **각각 찾아 대조**해야 합니다.
기관마다 지역 단위(행정동·상권·법정동)와 업종 분류가 달라 *같은 자리를 비교하는 것부터* 수작업입니다.

더 큰 문제는 **순서**입니다. 입지를 먼저 정한 뒤 자금을 알아보기 때문에, 보증금과 인테리어를 치르고 나서야 운영자금이 모자란다는 사실을 발견합니다.
신생기업 5년 생존율은 33.8%에 그칩니다.

> **목표:** "입지 → 자금" 순서를 **"자금 여력을 알고 → 자리를 고르는"** 순서로 바꾼다.

## 2. 목표

1. 6개 기관 공공데이터를 하나의 **분석용 DB**로 통합 (지역 코드·업종 분류 정합)
2. 업종·예산·목적만 입력하면 상권을 **6개 축으로 평가해 TOP 10 추천**
3. 부족자금을 계산하고 **정책자금·보증 조합으로 조달 설계**
4. 자연어 질문을 실제 분석 작업으로 수행하는 **도구 호출형 AI 에이전트**. 단, AI가 숫자를 지어내지 않게 할 것

## 3. 서비스 흐름

```
 조건 입력            상권 랭킹                 분석 리포트              금융 설계
 업종 8종 · 목적 ──▶ 6축 적합도 점수 ──▶ 지표 상세 · 개설비용 ──▶ 부족자금 → 정책자금·보증
 운영형태 · 예산       TOP 10 + 추천 근거       월 고정비 · PDF 저장      조합 · 월 상환액 · 손익분기 매출선
                               ▲
          "강남에서 1억 5천으로 카페 자리 찾아줘" ── AI 입지 어드바이저 (자연어 → 도구 호출)
```

## 4. 핵심 구현

### ① 공공데이터 통합 DB (SEOUL DB, SQLite 26개 테이블)
| 출처 | 데이터 |
|---|---|
| 서울 열린데이터광장 | 생활인구(**370만 행**), 상권분석서비스(영역·추정매출·점포·직장인구·상권변화) |
| 소상공인시장진흥공단 | 상가(상권)정보 → 경쟁 점포 수 |
| 한국부동산원 R-ONE | 임대료 · 공실률 · 전환율 |
| 국토교통부 | 상업·업무용 실거래가 |
| 국가철도공단 · 서울시 | 도시철도역 · 버스정류소 위치 |

- **지역 단위 정합**: 법정동은 매핑 테이블로 행정동에 연결하고, 부동산원 상권명은 자치구 대응표를 만들어 맞췄습니다. 서로 다른 업종 분류 두 가지는 매핑표로 8개 UI 업종에 연결했습니다.
- **분석 단위**: 행정동이 아니라 <b>서울시가 정의한 상권(1,030곳)</b>을 썼습니다. 행정동 경계는 실제 상권 범위와 맞지 않기 때문입니다.
- **사전 집계 캐시**: 생활인구 370만 행을 요청마다 계산하지 않고, 상권 단위로 미리 집계해 `areas.json`에 저장했습니다.

### ② 6축 적합도 스코어링 (결정론적 계산)
수요 · 업종적합 · 교통 · 생활인프라 · 예산적합 · 안정성의 6개 축을 정규화한 뒤, **창업 목적별 가중치**로 합산합니다.

| 창업 목적 | 수요 | 업종적합 | 교통 | 인프라 | 예산적합 | 안정성 |
|---|:-:|:-:|:-:|:-:|:-:|:-:|
| 상권 활성도 | **0.30** | 0.24 | 0.14 | 0.12 | 0.10 | 0.10 |
| 안정 운영 | 0.16 | 0.20 | 0.10 | 0.14 | 0.16 | **0.24** |
| 초기비용 절감 | 0.14 | 0.18 | 0.08 | 0.10 | **0.38** | 0.12 |

- **운영 형태에 따라 '수요'의 정의가 바뀝니다.** 방문 중심이면 유동인구를, 배달 중심이면 배후 주거·직장 인구를 쓰고 교통 가중치를 낮춥니다.
- 예산을 넘는 후보는 제외하지 않고 **감점**합니다. 하드 필터링을 하면 후보가 대부분 사라지는 문제를 발견하고 바꾼 것입니다.

### ③ 도구 호출형 AI 에이전트 — "AI는 숫자를 만들지 않는다"
```
 Understand                    Plan & Act                          Explain & Verify
 의도·슬롯 추출(지역·업종·예산)  ─▶ 허용 도구 선택 · 인자 스키마 검증  ─▶ 추천/비추천 근거 · 출처 · 기준시점
 누락 슬롯 재질문 · 대화 상태 유지   서버 계산 결과만 사용               불확실하면 보수적 폴백
```
- **에이전트 도구 7종**: `search_areas`, `get_area_detail`, `compare_areas`, `simulate_finance`, `get_national_region`, `explain_metric`, `list_options`
- **역할 분리**: LLM은 *이해·계획·설명*만 맡고, 점수·비용·상환액은 모두 서버 코드가 계산합니다. 프롬프트에서 새 수치 생성과 매출 예측을 금지했습니다.
- **멀티 프로바이더 + 폴백**: Gemini, GPT, Claude를 같은 도구 포맷으로 추상화했습니다. 한 모델에 장애가 나면 다음 모델로 넘어가고, 키가 없으면 **규칙 기반 해설로 자동 전환**됩니다.
- **테스트**: 실제 API 키 없이 Mock 서버로 3개 프로바이더의 tool-calling 변환과 장애 전환을 검증합니다(`npm test`, 4/4 통과).

### ④ 전국 확장 (서울 DB + 전국 API·캐시 병행)
- SGIS(인구·사업체), 소상공인365(매출), LOCALDATA(개·폐업 375만 건), R-ONE(임대료 276개 상권)을 결합해 **17개 시도 · 252개 시군구 · 3,563개 행정동**까지 분석합니다.
- 서울은 상권 단위, 그 외 지역은 행정동 단위로 **해상도가 다르다는 점을 숨기지 않고** 화면과 AI 설명에 표시합니다.

## 5. 데이터 품질 검증 — 반복 검증으로 발견·조치한 문제

| 단계 | 발견한 문제 | 조치 |
|---|---|---|
| 원본 적재 | CSV 파싱 옵션 누락으로 컬럼 밀림 | 재적재 + 검증 로직 추가 |
| 매출 파생 지표 | 상권과 배후지의 공간 범위 불일치로 **약 84배 과대추정** | 같은 범위끼리만 연산하도록 원칙화 |
| 상권 공간 매칭 | 폴리곤 중첩으로 점포 **17,489건 중복** | 정제 매칭 테이블 별도 구축 |
| 업종적합 점수 | 다중 코드 카테고리에서 행 중복 | 점포 수 가중평균으로 수정 |
| 보증금 추정 | 연 환산을 잘못 적용해 8~10배 과대추정 | 벤치마크와 대조해 산식 수정 |
| 매출 결측 | 587개 조합의 매출 통계 결측 | 자치구 → 서울 평균 순 **계층적 대체**로 결측 0건. 관측값·대체값·가정값을 구분해 표시 |

## 6. 설계 원칙 — 매출을 예측하지 않는다

같은 상권·같은 업종이어도 운영 역량에 따라 편차가 커서, 신뢰할 수 있는 매출 구간을 제시하기 어렵다고 판단했습니다.
그래서 **매출·영업이익·회수기간 예측을 제거**하고, 관측된 지표와 *고정비·상환액에서 역산한 손익분기 매출선*만 제공합니다.
지표 산출식, 가중치, 가정값, 데이터 한계는 모두 서비스 안 [데이터 안내](data.html) 페이지에 공개했습니다.

## 7. 한계 및 개선 방향
- **가중치**: 지금은 선행연구와 도메인 판단으로 정한 규칙 기반 가중치입니다. 사용 데이터가 쌓이면 학습 기반 가중치로 바꿀 계획입니다.
- **결제·인증**: 코인 차감은 현재 클라이언트(`localStorage`)에서 처리합니다. 정식 서비스라면 서버 트랜잭션(Firebase Functions 등)으로 옮겨야 합니다.
- **평가**: 질문셋 기반 E2E 평가(의도 이해·도구 선택 정확도, 재현율)를 다음 단계 KPI로 설계해 두었습니다.

## 8. 실행 방법

```bash
cd server
cp .env.example .env     # (선택) AI 키 입력. 없으면 규칙 기반 해설로 동작
npm start                # http://localhost:8787  — 패키지 설치 불필요 (Node 22.5+)
npm test                 # 프로바이더 tool-calling · 폴백 테스트
```
- `index.html`을 서버 없이 바로 열면 목업 데이터(상권 15곳)로 동작합니다.
- 원본 DB(`seoul_db.db`, 약 494MB)는 용량 문제로 제외했습니다. 대신 **상권 1,030곳의 사전 집계 캐시**(`server/cache/areas.json`)를 포함해서, 서버는 실데이터로 실행됩니다.
